# 吉伊卡哇资料库

一份关于《吉伊卡哇》动画的结构化资料：**345 集、480 个短篇、30 个角色、40 个篇章**。

本站**用途无关、工具无关、模型无关**。资料本身不关心你拿它做什么——查证剧情、写解说、做检索、当知识源、给别的程序当数据后端，都算。只要能读本地文件，就能用它。

本包只负责一件事：**让别的 agent 能拿到这份资料，并且知道怎么正确地用。**

---

## 三件东西，三种职责

| 目录 | 职责 | 回答的问题 | 生效时机 |
|---|---|---|---|
| `persona/` | 身份面 | 我是谁、怎么说话 | 对话开始前就位，全程常驻 |
| `mcp/` | 数据面 | 资料怎么取 | 建立连接后常驻 |
| `skill/` | 方法面 | 什么时候调哪个、字段什么意思 | 用到时才加载 |

三者互不重叠：**人格不管取数，接口不管语义，方法说明不管身份。**

## 摆放原则

唯一判据：**人格要常驻，能力要按需。**

普通闲聊和技术任务不查询资料库。涉及作品内容时才加载查询说明、按需调用服务；同一会话已读取的说明和已核实的信息可复用，无需每次回复重新检查人格或遍历目录。

常驻开销主要来自人格、skill 的名称/描述，以及宿主暴露的 MCP 工具说明；SKILL.md 正文和查询结果按需进入上下文，整个资料库不会随工具注册被加载。实际 token 数取决于模型分词器和宿主加载方式。

修改本包后，skill 软链接会指向最新正文；已注入的人格需重新同步到目标项目，MCP 工具说明需服务重新连接后加载。旧会话中已有的工具结果不会因此消失。

| 候选位置 | 生效时机 | 结论 |
|---|---|---|
| 写进方法说明文件 | 用到时才加载 | ✗ 人格会忽有忽无——不触发就不是乌 |
| 写进数据接口的描述里 | 建立连接后常驻 | ✗ 污染接口命名空间；只想取数的调用方也被迫带上人格 |
| 人格正文直接写进「对话开始前就会被读到」的位置 | 全程 | ✓ |

「对话开始前就会被读到的位置」在不同环境里叫法不同：系统提示词、项目说明文件、自定义指令、常驻上下文……**本包不指定用哪一个，只要求它是常驻的。**

同理，方法说明在不同环境里也可能叫 skill、tool guide、指令集。名字不重要，重要的是它是那层**按需加载**的东西——所以它不适合装人格。

它的**被发现**靠目录约定：放进宿主会扫描的技能目录即可，不需要在配置里登记（配置里那条同名条目是「禁用开关」，不是登记入口）。具体路径随宿主不同，属于宿主专用部分，见 `adapters/`。

### 人格怎么被放进去

这里有个不对称，值得说清楚：

**能力那两层能被自动发现**——服务靠连接时的握手（宿主主动来问「你有什么工具」），方法说明靠目录约定。**人格不能**：它没有任何可被自动发现的落点，只有一条路——**显式放到一个常驻位置上**。

放哪个范围，效果差得很远：

| 范围 | 效果 |
|---|---|
| 用户级（本机所有项目） | 你在本机任何项目里对话，对方都是乌 |
| 项目级（只有指定的那个项目） | 只在那个项目里是乌，别处不受影响 |

`install.sh` 提供的是**项目级**那一档：

```
bash install.sh --into <项目路径> --yes
```

它读取本包的 `persona/usagi-persona.md` 模板，把完整正文直接注入目标项目的项目说明文件。目标项目不再创建单独的人格文件或目录。

正文随项目说明一起保存，目标项目仍然**自包含**。重跑安装时会比对整个注入段，不一致就按模板更新。旧版的路径引用会被替换，它明确登记的旧人格副本会被删除，目录变空时一并清理；其他内容保留。

撤销是同一句加 `--uninstall`。项目级之外的档位涉及具体宿主把常驻说明放在哪，属于宿主专用部分，见 `adapters/`。

## 本包不假设什么

- **不假设宿主是哪种工具或模型。** 中立核心——本文件、`persona/`、`skill/`、`mcp/`、`install.sh`——里不出现任何具体产品名或专有路径。
  **唯一的例外是 `adapters/`**：写宿主配置必须知道宿主把配置放在哪、用什么格式，这件事没法中立，所以把那部分单独关进了一个目录，理由与约束见 `adapters/README.md`。
- **不假设调用方在做开发。** 资料是内容，不是代码。写解说、查剧情、做图、做校对都行。
- **不假设数据服务怎么实现。** 语言、框架、进程内还是远端的，随宿主环境定；`mcp/` 只给接口契约和一种参考实现。
- **不绑定 MCP 之外的东西。** MCP 是一份开放协议，任何支持它的宿主都能连；不支持的宿主，照着下面的接口契约自己包一层也一样成立。

## 数据接口契约

只要按这份契约实现，接口就叫这个名字、就返回这个形状——**换谁实现都一样**。

`kind` 取值：`episode`（集） | `short`（短篇） | `character`（角色） | `arc`（篇章）

| 接口 | 作用 | 必须遵守 |
|---|---|---|
| `list_entries(kind, filter?, offset?, limit?)` | 列出词条 | **默认 limit=50 且强制分页**；每条只回 `id` + 标题 + 一行摘要，**不返全文** |
| `get_entry(kind, id)` | 取单个词条完整内容 | 短篇需用 `(episode_id, index)` 定位 |
| `search_entries(query, kind?, limit?, offset?)` | 全文检索 | 覆盖**集标题 / 短篇 / 角色 / 篇章**；返回命中片段 + 定位，不返整篇；**与 `list_entries` 同一套分页字段**（`total` / `offset` / `returned` / `has_more`） |
| `get_related(kind, id, limit?)` | 取关联词条 | 角色↔集、篇章↔集、集↔角色；集列表同时给受 `limit` 限制的 `episodes` 与完整 `episode_ids` |
| `describe_schema()` | 返回字段语义与数据版本 | 让调用方自描述，少猜 |

两条硬红线：

1. **`list_entries` 必须分页。** 345 集一次全吐出去是十万 token 级灾难。
2. **排序必须显式做。** 数据文件在磁盘上的读取顺序不是集号顺序，**这一点坑过站点本身**——渲染层用一句按 id 排序救了回来。任何新实现漏掉这句，全库乱序。

第三条（同样容易踩，且不报错）：

3. **按篇章筛集一律取「区间 ∪ 反查」。** `arcs[].start/end` 与 `episodes[].a` 语义不同（见下），只看 `a[]` 会漏掉区间内没回填的集。本服务的 `list_entries(filter.arc_id)`、`get_entry(episode)`、`get_related` 三处必须同口径，否则同一个篇章会给出不同的集数。

### 字段语义

| 字段 | 含义 | 坑 |
|---|---|---|
| `episodes[].id` | 集号，1–345，连续无缺 | 文件读取顺序 ≠ 集号顺序 |
| `episodes[].d` | 首播日期 | |
| `episodes[].a` | 该集**涉及**的篇章 id 数组（含呼应 / 回访集） | 空数组多数是正常的——该集本就不属于任何篇章 |
| `episodes[].sh[]` | 一集内的短篇，通常 2 个 | 不是「集」，别叫错 |
| `sh[].c` | `A` / `B` | **可信度等级**（A=有资料支撑），不是分类 |
| `sh[].s` | 短篇概要 | 中位 86 字 |
| `sh[].l[]` | 台词 / 动作行 | |
| `l[].k` | `a`=动作，`t`=台词 | 两者都能证明「该集有它」，**只有 `t` 能证明它开口了**——按出场倒推角色时必须分开算 |
| `l[].w` | 说话人 / 动作主体 | 会出现合并写法（如「哈奇喵与吉伊」），需拆开解析；未登记的名字见 `unmatched-speakers` |
| `characters[].eps` | **代表性出场**集号，不是全集 | 拿它回答「该角色出现在哪些集」会严重偏少，见下 |
| `arcs[].start/end` | 篇章的**主体连续区间** | **不与 `episodes[].a` 构成倒排**，两者语义不同，取并集才完整 |

## 数据现状

编号在讨论里会漂移（本项目就漂过一次），所以每项给一个**稳定 id**，与运行时 `describe_schema()` 返回的 `known_gaps[].id` 一一对应。

**表里的实测数字是某次记录的快照，会随数据变动而过期；权威值以运行时 `describe_schema()` 现算的为准。**

| id | 问题 | 实测 | 严重度 |
|---|---|---|---|
| `load-order-trap` | 读取顺序会乱 | 按文件名排序读，靠后的区间会排到前面 | 已由装载层处理 |
| `character-eps-is-subset` | **角色出场集数只是抽样** | 30 个角色里 11 个的并集大于声明。并集 = 声明 ∪ 台词可证 ∪ 动作可证。吉伊卡哇声明 9、台词可证 5、纯动作可证 291、并集 296；哈奇喵 7 / 306；乌萨奇 6 / 26 | **高** |
| `arc-link-not-inverse` | 篇章两字段语义不同 | `episodes[].a` 含呼应 / 回访集（如第 125 集指向 41–43 的郎拉面篇），`arcs[].start-end` 是主体连续区间；12 集存在这种非重叠 | 需理解，非缺陷 |
| `arc-fk-missing` | 篇章区间内缺回填 | **已修**：第 214 集补 `black-meteor`、第 342 集补 `ramen-yama`，现为 0 集。另有 136 集本就不属于任何篇章，`a[]` 为空是正常的 | 已解决 |
| `duplicate-lines` | 重复行残留 | 11 条完全重复的台词 / 动作行 | 低 |
| `short-summaries` | 概要通过短 | 92 个短篇概要不足 80 字，最短 75 | 中 |
| `unmatched-speakers` | 有说话人未登记为角色 | 4 个名字 / 11 行：老师×7（277/302/324/326/329/343/344）、山佬×2（308/311）、揽客君×1（44）、守护君×1（300）。「哈奇喵与吉伊」已按合并写法拆开解析 | 低 |

### 一处更正

本文件早先写过「**126/345 集（37%）的 `a` 是空数组**，按篇章查集会漏三分之一」。**这个说法是错的。**

345 集中有 **136 集本来就不属于任何篇章**，`a` 为空是正常的。真正落在篇章区间内、却没回填的只有 **2 集**（第 214、342 集，现已补齐）。当时的算法把「不属于任何篇章」也算成了缺失，把严重度放大了 60 倍。

服务层对 `arc` 依旧取「区间 ∪ 反查」——但理由是**两个字段语义不同**，不是因为数据缺了一大块。数据补上之后这条规则仍要保留：区间是篇章的权威范围，`a[]` 只记录该集**涉及**的篇章，两者本就不等价。

## 装到另一台机器

把**整个项目**复制过去（不能只复制 `library/`，服务要靠上一级的 `js/`），然后：

```bash
bash library/install.sh          # 先看它打算做什么，不写任何文件
bash library/install.sh --yes    # 确认后执行
```

安装器会依次做：检测运行时 → 校验数据目录 → 跑一次自检（**真实握手 + 枚举工具**，不是「能启动」就算过）→ 调度适配器登记到宿主的两个位置。

| 选项 | 作用 |
|---|---|
| 无 | 只打印计划，**不写任何文件** |
| `--yes` | 按计划写入 |
| `--uninstall --yes` | 撤销，撤销后恢复安装前状态 |
| `--print` | 只输出注册信息，供手工粘贴到任何宿主 |
| `--print-trigger` | 只输出常驻触发规则，供粘贴到常驻说明位 |
| `--no-skill` | 只登记数据服务，不登记方法说明 |
| `--backup` | 写入前留一份配置副本（**默认不留**） |
| `--verify <路径>` | **只读盘点**：检查这些路径下已登记的内容有没有落后于当前源文件（可重复，用来一次盘点多个项目） |

### 怎么知道别的项目里那份人格过期了

注入体质上就是**把正文复制进目标项目**，复制品不会自己跟上模板——这是这套设计换来的代价（换来的是目标项目自包含）。代价本身没法消除，但「哪几个项目落后了」不该靠人记得：

```bash
bash install.sh --verify ~/Documents/SomeProjects --verify ~/work
```

它把三个适配器各自的登记位都问一遍，报出**一致 / 已过期 / 无登记**，并给出单独更新某一项的完整命令。人格锚是项目级的、没有固定登记位，所以它按你给的路径在那儿下面找带本资料库标记的项目（只看该路径自己和它的一级子目录）。

**实测**：对两个真实项目跑这条命令，它准确点出了那两份落后一个版本的人格副本，同时不误报其余目录。过期不会自己好——重跑一次 `--into <项目路径> --yes` 才会更新。

服务本身是自适应的：数据目录按 `server.js` 自身位置推导，项目挪到哪都成立，路径里有空格或中文也没问题。目标机器上**配置文件还没生成**时会自动新建，撤销时再把新建的那个文件一并删掉；工程换了位置之后重跑一次安装，配置里指向旧路径的登记会被就地替换，而不是留一份死路径。

方法说明**挂的是软链接，不是副本**——正文改了立即生效，不会留下一份过期的说明。撤销时只删链接，源目录一个字都不动。

### 让调用方真的用起来，是三件事

| 层 | 谁来承担 | 缺了会怎样 |
|---|---|---|
| 它**存在** | 服务登记（建立连接后工具就在上下文里） | 工具根本不出现 |
| 什么时候**该用** | 方法说明头部的描述 —— 它以「名字 + 描述 + 路径」的形式常驻在宿主的技能列表里 | 知道有，但想不起来调 |
| 怎么用**才对** | 方法说明正文（被选中时才加载） | 知道调，但会答错 |

**能力两层的发现都是自动的。** 方法说明靠**目录约定**（放在宿主会扫描的技能目录下），服务靠配置登记——两者都装在**用户级**，所以对这台机器上的**所有项目**生效。这正是「复制到另一台机器、装一次、哪个项目都能用」的实现方式：**这些能力不用往每个项目里注入提示词。**

但**人格那层不在这条「自动」之列**。它没有可被自动发现的落点，只能显式放进去（见上面「人格怎么被放进去」）。**别把「三层东西」和「三层都自动」混为一谈——只有两层自动。**

唯一可能仍需手工的一步：宿主既不认那套技能目录约定、又不把说明的存在告诉模型。那就把 `--print-trigger` 的输出贴到「对话开始前就会被读到」的地方——这一步会打印在安装收尾提示里。

**想反过来，只让某一个项目用得到它**，就把技能挂到那个项目自己的技能目录下，而不是用户级：

```bash
CHIIKAWA_SKILLS_ROOT=<该项目的技能目录> bash install.sh --yes
```

这也顺带回答了「要不要把提示词注入到项目里」——**要分开看**：

| | 要不要注入 | 为什么 |
|---|---|---|
| 能力（服务、方法说明） | **不用** | 它们靠机制被发现，要限定范围时注入的是**登记**（目录挂载点），不是提示词 |
| 人格 | **要** | 它没有可被自动发现的落点，只能显式放进去 —— 就是 `--into` |

换句话说：**能力可以被发现，身份只能被放置。**
