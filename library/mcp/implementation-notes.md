# 数据面 · 一种参考实现

本文件是**实现细节**，不是契约。接口叫什么、返回什么形状，看 `../README.md`。
下面这套做法只是其中一条路，换成别的语言、别的进程模型、甚至远端服务，只要符合契约就同样成立。

---

## 怎么跑起来

**这是 stdio 形态：没有端口、没有 URL、没有鉴权。** 宿主按需把 `server.js` 拉起成一个子进程，通过标准输入输出收发 JSON-RPC，宿主退出它也跟着结束。所以不需要"启动服务"这一步，也不需要管端口冲突。

需要准备的东西：

- 一个 Node.js 运行时（只用内置模块，**无第三方依赖，不用装包**）
- 数据目录（默认取工程根的 `js/`；要指到别处就设环境变量 `CHIIKAWA_DATA_DIR`）

在宿主的 MCP 服务清单里登记一条，通用形状大致是：

```json
{
  "command": "<node 可执行文件路径>",
  "args": ["<本目录绝对路径>/server.js"]
}
```

**具体字段名以你的宿主文档为准**——各实现对 `command` / `args` / `env` 的叫法基本一致，但配置文件放哪、怎么写不统一，本包不假定。

这里有个容易踩的点：stdio 形态下 **stdout 只能是 JSON-RPC**，写进去任何别的东西都会让宿主解析失败。本实现的日志一律走 stderr。

### 自检

不确定数据装载是否正常时，直接跑：

```
node server.js --selftest
```

它会把字段表、数据规模、版本指纹和已知缺口打成 JSON 输出后退出，不进入服务状态。快速排查用它，比接宿主快。

## 数据在哪

```
js/
├── episodes-01-40.js      # 剧集，9 个文件按区间切开
├── episodes-41-80.js
├── episodes-81-120.js
├── episodes-121-160.js
├── episodes-161-200.js
├── episodes-201-240.js
├── episodes-241-280.js
├── episodes-281-320.js
├── episodes-321-345.js
├── data-characters.js     # 角色
└── data-arcs.js           # 篇章
```

共 11 个文件、约 294KB。它们不是 JSON，而是**给浏览器用的赋值脚本**：

```js
window.CK = window.CK || {};
window.CK.episodes = (window.CK.episodes || []).concat([ ... ]);
```

所以装载方式是：**造一个假的 `window`，把这些文件跑一遍，然后把 `window.CK` 取出来。**
不需要转成 JSON，也不需要落库——**保持这份脚本是唯一数据源**，否则站点改了、副本没跟上，答出来的就是错答案。

## 有一个文件不能跑

`js/app.js` 是渲染层，内部依赖浏览器环境（读 `location`、操作 `document`）。**别装载它。**

代价是：排序逻辑写在它里面，得复制一份到实现里。见下。

## 装载与索引

伪代码，语言自选：

```
ctx = sandbox({ window: {} })
for f in 11 个数据文件:
    ctx.run(读文件(f))

CK = ctx.window.CK
episodes  = CK.episodes.slice().sort(by id)   // ← 这句不能省
characters = CK.characters
arcs      = CK.arcs
```

启动时跑一次，索引建在内存里：

- `byId`：集号 → 集、角色 id → 角色、篇章 id → 篇章
- `arcIndex`：篇章 id → 集号集合，**两个方向都要取**——`arcs[].start/end` 的区间，加上 `episodes[].a` 的倒排，合并成一个集合。单看任一边都会给出错的集数：只看 `a[]` 会漏掉区间内没回填的集，只看区间会漏掉呼应/回访集。装载时预计算一张「集 → 篇章」的反查表，之后每次调用都直接查表，不再重扫区间。
- `charIndex`：角色 → 集号集合。**台词行与动作行要分开记**（`l[].k` 为 `t` / `a`）：两者都能证明「该集有它」，但只有台词能证明它开口了。合成一个数会让「出场集数」看起来远大于实际，且无法解释。
- `textIndex`：集标题 + 短篇概要 + 台词的全文可检索形式

## 排序这条红线

数据文件在磁盘上的读取顺序不是集号顺序。站点靠渲染层里一句「按 id 排序」救了回来，**但那是渲染层的职责，数据层本身没有这个保证**。

任何新实现漏掉排序，表现是：目录页乱序、范围查询返回错区间、翻页错位——而且**不会报错**，只会安静地给错结果。所以这句排序要写在装载层，不是展示层。

## 关于缓存

**进程内一次装载就够了。** 294KB 进内存、扫 480 条短篇，实测量级在 10ms 以内。

不建议做的：

- **磁盘缓存 / 序列化中间态** —— 多一份可能过期的副本，换来几毫秒。
- **关系型数据库** —— 记录数约 800 条，加了索引也只快约 9ms，却引入"改了源文件忘了刷库"这个会**答错**的故障模式。

值得做的，只有一种：**给数据源算一个版本指纹**（文件内容哈希或修改时间），由 `describe_schema()` 返回。调用方据此判断手上的结果是不是旧的。

## 什么情况下才该上数据库

满足任一条再说：

- 记录数到万级（现在约 800）
- 有多个写入方（现在纯只读）
- 需要事务、并发写、历史版本回溯
- 需要跨实体的复杂聚合（现在 30 角色 × 40 篇章的规模，内存里几行就写完）

## 开工前

数据现状 7 个已知项列在 `../README.md`，与 `describe_schema()` 返回的 `known_gaps[].id` **一一对应**。讨论时请用 id 指代，不要用编号——编号在本项目漂过一次，是乌的报告问题。

真正够得上「开工前该修」的那一项（`character-eps-is-subset`）**已经修好了**——不是靠改数据，是靠**把口径摊开**：`get_entry` / `get_related` 现在回 `declared` / `from_speaking` / `from_actions` 三个数，外加互斥拆分 `spoken_only` / `acted_only` / `both`。调用方一眼能看出「并集里有多少只是动作推出来的」，不会再把它当成「这些集它都说过话」。

`arc-fk-missing` 则从数据侧修掉了：第 214 集补 `black-meteor`、第 342 集补 `ramen-yama`，现为 0 集。但**服务层那条「区间 ∪ 反查」不能因此删掉**（见上），它是语义要求，不是数据补丁。

其余各项的处置：

| id | 处置 |
|---|---|
| `load-order-trap` | 已由装载层处理，消费者无需额外动作 |
| `arc-link-not-inverse` | 不是数据问题，是语义要用对：取并集，别拿单边当真值 |
| `arc-fk-missing` | 已补数据；服务层仍取并集 |
| `duplicate-lines` / `short-summaries` / `unmatched-speakers` | 影响答案质量，不影响正确性。未登记说话人现在会连同所在集号一起返回，可直接定位去补 |
