# 适配器 · 宿主专用，不属于中立核心

这个目录是**故意破例的地方**。

资料库包本身要求用途无关、工具无关、模型无关——`README.md`、`persona/`、`skill/`、`mcp/`、`install.sh` 里都不出现任何具体宿主的产品名或专有路径。

但「一键安装」这件事没法中立：**登记到宿主必须知道宿主把东西放在哪、用什么格式。** 所以把这部分单独关进这个目录：

| 目录 | 允许出现宿主名 | 说明 |
|---|---|---|
| `library/`（除本目录） | **不允许** | 中立核心，换任何宿主都一样 |
| `library/adapters/` | 允许 | 每个登记位一个脚本，**只在这里破例** |

目前有三个：

| 脚本 | 登记什么 | 登记在哪 |
|---|---|---|
| `toml-mcp-servers.sh` | 服务的启动命令与参数 | 宿主的配置文件（TOML 表） |
| `agents-skills-dir.sh` | 方法说明 | 宿主的技能扫描目录（软链接） |
| `agents-md-file.sh` | 人格正文 | **指定项目的 AGENTS.md**（直接注入完整模板正文） |

前两个是**用户级**：装一次，本机所有项目都能用。
第三个是**项目级**：目标项目必须由调用方显式指定（`--into <项目路径>`），没指定就不参与安装 —— 人格没有可被自动发现的落点，只能这样显式放进去。

## 契约

每个适配器是一个可执行脚本，通过环境变量拿参数。**五个子命令是必须实现的**：

| 环境变量 | 含义 |
|---|---|
| `CHIIKAWA_NAME` | 服务名，写进配置用的标识 |
| `CHIIKAWA_NODE` | 运行时的绝对路径 |
| `CHIIKAWA_SERVER` | `server.js` 的绝对路径 |
| `CHIIKAWA_SKILL` | 方法说明文件的绝对路径；为空表示不登记 |
| `CHIIKAWA_SKILLS_ROOT` | 方法说明挂到哪个目录。默认用户级，对所有项目生效 |
| `CHIIKAWA_PERSONA` | 人格正文模板的绝对路径；为空表示这一层不参与 |
| `CHIIKAWA_TARGET_PROJECT` | 人格锚注入到哪个项目。为空表示不注入 |
| `CHIIKAWA_VERIFY_ROOTS` | **只在盘点时给**：冒号分隔的路径，供没有固定登记位的适配器（如人格锚）在那下面找自己留下的东西 |
| `CHIIKAWA_BACKUP` | `1` 表示写前留一份副本，默认不留 |

**登记位**可以是配置文件、一个目录，也可以是**一个项目根** —— 各适配器按自己宿主的机制定。下面用 `<登记位>` 指代。

| 子命令 | 行为 |
|---|---|
| `detect` | 逐行输出**可写入**的登记位路径，没有就输出空。全新机器上配置文件往往还没生成，所以「文件的上级目录存在」也算可写入，由 `apply` 负责新建。**没有固定登记位的适配器改用 `CHIIKAWA_VERIFY_ROOTS` 在那下面找。** |
| `installed <登记位>` | **已登记且内容一致**（无需改动）则退出码 0，否则非 0 |
| `plan <登记位>` | 打印将要做什么，不落盘。要写清楚是「新建」「追加」还是「替换过期的」 |
| `apply <登记位>` | 真正写入／挂载 |
| `remove <登记位>` | 撤销自己登记的东西。**撤掉了就退出码 0，没得撤就非 0** —— 用退出码表达，不谎报成功 |

### 可选的第六个子命令：`status`

`installed` 只回答「要不要动手」，回答不了「现在是什么状态」。所以适配器**可以**再实现一个 `status`，把状态和退出码一起给出来：

| 退出码 | 含义 |
|---|---|
| 0 | 已登记且与当前一致 |
| 1 | 已登记，但内容过期（源换了位置、模板改过） |
| 3 | 这个位置没有本服务的登记 |
| 2 | 没实现 status（适配器直接走 `*)` 分支）—— 调用方据此跳过，不是错误 |

有它之后，`install.sh --verify <路径>` 才能把「哪几个项目的人格已经落后于模板」一次列出来。**这不是「复制品会自己跟上」的意思** —— 注入体质上就是复制正文，复制品不会自己更新，`status` 只是让这件事从「靠人记得」变成「一条命令」。

### `installed` 判的是「内容一致」，不只是「标记在」

这一条容易做错，后果也最隐蔽：如果只检查「我留下的标记还在」，那么**工程换了位置之后**，登记里那行指向旧路径的死配置会被判成「无需改动」，重跑安装也修不回来——用户看到的是一份永远指向旧位置的登记。

正确做法是连**值**一起比对；不一致就让 `installed` 返回非 0，由 `apply` 就地替换掉旧的那份（而不是再追加一份）。

## 硬要求

动的是**用户机器上的全局位置**，所以每个适配器都必须：

1. **只动自己那一块** —— 别人写的内容一个字节都不碰
2. **幂等** —— 重复执行不产生第二份
3. **可撤销** —— `remove` 要干净，且删完与安装前一致
4. **绝不覆盖不是自己建的东西** —— 目标位已被占用且不属于本适配器时，**报错退出**，不猜、不强行接管
5. **不自动留副本** —— 默认不留；`--backup` 是显式选择
6. **能被 dry-run** —— `plan` 与 `apply` 分离

## 加一个宿主

1. 在本目录新建一个脚本，**用配置格式或目录约定命名**，不要用产品名
2. 实现上面五个子命令
3. 把它认的位置填进脚本里的候选列表
4. `install.sh` 会自动发现它，不用改核心

命名用**格式／约定**（如 `toml-mcp-servers`、`agents-skills-dir`）而不是产品名 —— 这样同一个适配器能覆盖多个用同样格式或约定的宿主，也避免把某个品牌写进文件名。

## 三处登记位，各管一层

三层落在**三个不同的位置**，所以由三个适配器分别负责，各管各的、互不耦合：

| 层 | 登记位 | 撤销时 |
|---|---|---|
| 服务 —— 工具能被调用 | 配置文件里的一段 | 整段拿走 |
| 方法说明 —— 被选中时才加载 | 技能扫描目录下的一条软链接 | 只删链接，源目录不动 |
| 人格 —— 每次对话都在场 | 目标项目 AGENTS.md 里的完整人格正文段 | 摘掉那一段；文件因此变空时删除文件 |

**人格模板保留在资料库，安装时直接注入正文：**

`library/persona/usagi-persona.md` 是正文模板。目标项目只在 `AGENTS.md` 的标记段里保存正文，不创建 `.chiikawa` 目录或独立人格文件；安装回资料库自身也使用同一流程。`installed` 比较整个标记段与当前模板，不一致就由 `apply` 更新。

**`plan` 会顺带点名可能冲突的既有规则。** 注入是把一段身份说明追加到目标项目说明文件的**末尾**，而那个文件里往往已经有一条跟说话方式有关的约定（表情、语气、语言、角色扮演）。两条并存时后面那条更强势，结果是一个项目里同时存在互斥要求——实测出现过「项目要求保留表情规则、注入的人格禁用 emoji」这种组合。所以 `plan` 会扫一遍目标文件、把可能相关的行连行号列出来：

```
这段人格会追加到文件末尾，而该文件里已有这些规矩可能和它冲突，请自己确认：
  · 第 5 行：- 首次回复前读取并遵守 `Agent/personality/emote-rules.md`，保留表情规则。
```

**命中不等于冲突，等于「这行该由人看一眼」**——工具不做判断，也不改别人的规则。

兼容旧版未闭合的 HTML 标记：安装时替换旧的路径引用段，删除该段明确登记的 `.chiikawa/usagi-persona.md` 副本，目录变空时用 `rmdir` 清理。未被旧段登记的文件、目录内其他文件及源模板都保留。撤销旧版登记也按此规则清理。

**不要试图把方法说明登记进配置文件。** 它的发现靠**目录位置**；配置文件里那条同名条目是「禁用开关」（默认启用），拿它当登记入口是无效的——本包第一版就这么错过。

**也不要试图让人格走技能那条路。** 技能是**按需加载**的，人格要**常驻**；塞进技能里人格会忽有忽无——没被加载的那几轮就不在场了。

配置类适配器的标记段形如（语法随文件格式变，语义不变）：

```
# >>> <服务名> 资料库（install.sh 写入，撤销请跑 --uninstall） >>>
<要登记的内容>
# <<< <服务名> 资料库 <<<
```

在 Markdown 说明文件里同一对标记写成 HTML 注释（不显示，也不打断正文）：

```
<!-- >>> <服务名> 资料库 · 人格锚（install.sh 写入，撤销请跑 --uninstall） >>> -->
<人格模板的完整正文>
<!-- <<< <服务名> 资料库 · 人格锚 <<< -->
```

`remove` 只认这对标记，整段拿走，因此不会误伤别人写的内容。

> 不要用具体宿主的表名或文件名当契约。上面是**语义**（本服务的那一段），映射成什么语法、写进哪个文件，由各适配器自己定。

## 已知的还原差异

动的是用户机器上的全局位置，所以「撤销后与安装前一致」这条要说得精确，做不到的地方如实标注：

**1. 原配置文件结尾没有换行符时，撤销后结尾会多一个换行（差 1 个字节）。**

原因：追加前必须先补一个换行，否则标记会粘在上一行后面，配置语法就坏了；而「原来有没有结尾换行」这个信息在撤销时已无从判断（除非额外留状态文件，得不偿失）。

影响：**没有**。这类配置语法对结尾换行不做要求。其余情形（含连续空行）撤销后均与安装前逐字节一致。来回装撤多轮也不漂移。

**2. 原配置文件不存在（由本适配器新建）时，撤销会把这个文件删掉。**

结果为「这台机器上原本没有这个文件」，与安装前状态等价。但严格说不是「文件还在、只是空着」。

**3. 目录类登记：撤销时会顺手收掉因此变空的上级目录，但不会越过用户主目录。**

卸掉软链接后，如果技能目录空了，就把它、以及它那些同样空掉的上级一起 `rmdir`。`rmdir` 对非空目录必然失败，所以**目录里还有别人的东西时绝不会被动**。反过来的误差是：如果那个上级目录**本来就存在且是空的**，撤销后它会消失——与「空目录」的差别在功能上为零。

**4. dry-run 撤销对「过期的登记」会报「没有本服务」。**

`--uninstall` 不带 `--yes` 时靠 `installed` 判断有没有东西可撤，而 `installed` 判的是「内容一致」。所以登记存在但内容过期时，预览会说没有本服务。真加 `--yes` 执行时用的是 `remove` 的退出码，能正常撤掉。——只是预览文案不够准，不值得为它加一个子命令。

**5. 手工改过项目说明里的注入正文，下次安装会被模板覆盖。**

要统一修改人格，应编辑资料库的正文模板，再重跑安装。只更新本资料库的标记段，段外的项目规则保留；`plan` 会展示将要替换的完整正文。

**6. 目标项目里那个说明文件本来不存在（由本适配器新建）时，撤销会把它删掉。**

同第 2 条的语义：等价于「这个项目里原本没有这个文件」。
如果那个文件里还有你自己后来加的内容，不会丢——剥离只认那对标记，剥完还有别的东西就把文件留下。

**7. 配置类登记如果没有标记，撤销后那几行不会回来（这是预期行为）。**

标记对是后来才引入的写法，早期版本和手工粘贴留下的登记都没有标记。这种登记现在**认得出、也撤得掉**（按表段整段摘），但它本来就不是本适配器写的格式，撤销时无法还原成原样——撤完就是「这段登记没有了」，而不是「文件回到安装前」。

实测：把真实配置里一段无标记的 `[mcp_servers.<名字>]` 走一遍 `apply → remove`，73 个表头一个不少、邻居表原样、被拿掉的只有本服务那一段和它两边的空行。反过来，**带标记的登记来回装撤是逐字节一致的**（第 1 条那个结尾换行除外）。

判断手上是哪一种：`status` 会直说——带标记的报「一致」，不带的报「一致（但这一段没有标记，撤销时按表段整段摘）」。
