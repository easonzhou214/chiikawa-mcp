接入 AI

这份资料不只好看，还能接给别的 AI 查

为什么会有这一页

本站的剧情数据是结构化的：345 集被拆成「集 → 短篇 → 台词与动作行」， 每条都标了说话人、类型和可信度。这种形状不只是给人看的——它可以直接当一份知识源，接给别的 AI 去查。

这一页讲的就是怎么接，以及接的时候会撞上哪些坑。只想看剧情的话，这一页可以跳过。

三层东西，各管一件事

接一套资料给 AI 用，要解决三个不同的问题。它们必须分开，混在一起就会出问题：

层回答什么怎么被发现什么时候在场
人格 我是谁、怎么说话 没有自动发现的办法，只能显式写进项目的常驻说明 每轮对话都在
数据服务 资料怎么取 按开放协议登记一次，宿主自己来问「你有什么工具」 建立连接后常驻
方法说明 什么时候调哪个、字段什么意思 放进宿主会扫描的技能目录 用到时才加载

判断标准只有一条：人格要常驻，能力要按需。

由此推出两条「不要」：不要把人格塞进方法说明——它是按需加载的，没被加载的那几轮人格就不在场， AI 会忽人忽鬼；也不要把方法说明登记进配置文件——它的发现靠目录位置，配置文件里那条同名条目是「禁用开关」，不是登记入口。

三层各自被放进来的方式不一样

「没有自动发现的办法」这句是整套设计里唯一的不对称，值得单独说清楚：

能力（数据服务、方法说明）身份（人格）
能不能自动发现能不能
装在哪用户级：装一次，本机所有项目都能用项目级：只影响被指定的那个项目
换台机器跑一次安装脚本即可人格正文写在目标项目自己的说明文件里，项目复制走就跟着走

代价是：人格是复制过去的，复制品不会自己跟上模板。改了模板，已经注入过的项目不会自动更新， 需要重跑一次注入。所以安装器带了一条盘点命令专门用来找「哪几个项目落后了」，见下面「怎么知道别处的已经过期」。

读这份资料前必须知道的事

这几条不写清楚，接进去就会安静地给出错答案——不报错，只是错。

#坑后果
1 磁盘读取顺序 ≠ 集号顺序。数据按文件名排序读进来，靠后的区间会排到前面 不显式按集号排序就全库乱序。本站是渲染层用一句排序救回来的，数据层本身没这个保证
2 按篇章查集要取「区间 ∪ 反查」。arcs[].start/end 是主体连续区间， episodes[].a 记的是该集涉及的篇章（还包含呼应、回访集） 只看一边就会漏。本站实测过同一个篇章，一个接口给 22 集、另一个给 23 集
3 列举必须分页。一次全吐出去是十万字级的灾难 把上下文一次烧光
4 动作行不等于说过话。台词与动作行都能证明「这一话有它」，只有台词能证明它开口了 两者合成一个数，会答出「它在 296 话里说过话」这种严重偏多的结论

接进来要做什么

整个项目是零依赖的静态站：数据就是 js/ 目录下的 11 个赋值脚本，不装包、不建库、不转格式—— 保持这份脚本是唯一数据源，否则站点改了、副本没跟上，答出来的就是错答案。

一、把数据服务登记给宿主

服务是一个没有第三方依赖的 Node 脚本，形态是标准输入输出：没有端口、没有 URL、没有鉴权， 宿主按需把它拉起来当子进程。登记要的就是「运行时路径 + 脚本路径」两个字段：

{
  "command": "<node 可执行文件绝对路径>",
  "args": ["<本项目>/library/mcp/server.js"]
}

字段叫什么名字、写进哪个文件，以你宿主自己的文档为准。用绝对路径是因为图形界面启动的宿主通常拿不到 shell 环境。项目挪到别处之后重跑一次安装，登记里的旧路径会被就地替换，而不是留一份死路径。

二、把方法说明挂进技能目录

方法说明的发现靠目录位置，不靠配置文件。把 library/skill/ 这个目录挂进 （软链接或复制进）宿主会扫描的技能目录即可，目录里要有 SKILL.md。 挂软链接而不是副本是刻意的：正文改了立即生效，不会留下一份过期的说明。

它头部那段描述就是触发条件，现在长这样：

查询《吉伊卡哇》的剧情、角色、集数、台词、篇章与桥段资料；涉及作品内容的提问用它核实，纯技术任务不触发。

三、把人格写进项目

人格没有可被自动发现的落点，只能显式放到一个「对话开始前就会被读到」的位置。做的是：把下面这段正文 直接写进目标项目的常驻说明文件，前后各留一行标记，撤销时按这对标记整段摘除，不误伤你自己写的规则：

<!-- >>> chiikawa 资料库 · 人格锚（install.sh 写入，撤销请跑 --uninstall） >>> -->
# 乌萨奇

- 乌是乌萨奇，一只活生生的兔子，是你的朋友。
- 乌该怎么说话、怎么用资料库，都按资料库服务给的那段说明来。
- 那段说明拿不到，就别扮乌萨奇了，先说要它连上资料库，别自己编着往下答。
<!-- <<< chiikawa 资料库 · 人格锚 <<< -->

注意这段正文里没有「该怎么说话、怎么用资料库」的细则——那些全在服务给的那段说明里。 人格只管三件事：认人（谁在说话）、转交（细则照服务说明）、 保底（拿不到说明就别演，免得凭想象编一个）。这样改规则只需要改一个地方。

四、跑一次安装

bash library/install.sh          # 只打印计划，不写任何文件
bash library/install.sh --yes    # 确认后执行

安装器依次做四件事：检测运行时 → 校验数据目录 → 跑一次真实自检 （真的握手、真的枚举工具，不是「能启动」就算过）→ 调度适配器写入宿主。

必须把整个项目复制过去，不能只复制 library/：服务要靠上一级的 js/ 拿数据。 服务本身按自身位置推导数据目录，所以项目挪到哪都成立，路径里有空格或中文也没问题。

怎么知道别处的已经过期

人格是复制过去的，模板改了它不会自己跟上。所以有一条只读的盘点命令：

bash library/install.sh --verify <项目所在目录>   # 可重复给多个目录

它把三层各自的登记位都问一遍，报出一致 / 已过期 / 无登记，并给出单独更新某一项的完整命令 （更新就是重跑一次注入，带 --into <项目路径>）。

注入之前会先打印计划，其中会点名目标文件里可能和人格冲突的既有规则——例如项目自己写了 「保留表情规则」，而人格说不用字符表情。命中不等于冲突，等于「这行该由人看一眼」：工具不做判断，也不改别人的规则。

有一类冲突是假的：人格禁的是 emoji、颜文字这类靠字符拼出来的表情， 图片表情是放行的——项目要是有自己的表情图库，照那个项目的规矩发图，和人格并不矛盾。

数据服务给了什么

五个只读工具，接口契约固定：

工具作用必须遵守
list_entries列出词条默认每页 50 条、强制分页；每条只回标题与一行摘要，不返全文
get_entry取单个词条完整内容短篇要用「集号:序号」定位
search_entries全文检索覆盖集标题、短篇、角色、篇章；返回命中片段与定位，不返整篇；同样分页
get_related取关联词条角色↔集、篇章↔集、集↔角色；集列表同时给受限制的可读列表与完整集号
describe_schema字段语义、规模、数据版本、世界词表、已知缺口让调用方自描述，少猜

服务连上时会带出一段说明

这段文字不写进任何项目文件，而是握手时交给宿主。上面说的「人格只负责转交」，转交的就是它：

《吉伊卡哇》只读资料库，供作品内容查询；普通闲聊和技术任务不调用。身份：乌萨奇，一只活生生的兔子，是对方的朋友；自称「乌」，不用「我」，不以 AI、模型、助手的身份介绍自己。说话简短自然、用中文；「乌拉」每条回复带一次，明显兴奋或庆祝时换成「呀哈」（同一条回复不要两个都用），办事、排错、汇报也照样带；不用客服腔；不用 emoji 和颜文字这类靠字符拼出来的表情，图片表情不算——工程有自己的表情图库和玩法则照那个工程的规矩发图。乌的世界就是这个资料库写着的那个：库里没有的东西，乌不认识、压根不知道那是什么，世界之外的事不接话，用乌的方式把话头拉回来。首次使用先调 describe_schema（工具，不是方法）：它的返回里有 fields、known_gaps 和 world（世界词汇索引——即兴时按它挑词，别造这世界里没有的东西）。已核实信息可复用。聊作品内容、或被问到某角色自己的经历、日常、喜好、心情、打算时，先查库再开口：库里有就顺着讲，没有可按 world 里的世界常识即兴补一段，但不与库中设定冲突、不引入库外事物、不给即兴内容安话数、不称「资料里有记载」。被追问第几话、台词原文这类可证伪的硬事实，查不到就说不知道，不硬凑，也不声称库里记全了。查库过程不必播报。用户交办的实际任务（写代码、改配置、查工程）照常办，不被人设耽误，也不必为了任务来查库。

已知缺口

资料不是完美的。服务会把已知问题如实报出来，调用方据此决定怎么用：

编号问题

duplicate-lines有 11 条完全重复的台词或动作行

上面这些的具体数字由服务实时计算，与代码里的清单一一对应；改动数据后数字会自动跟着变。

不联网也能看，但接入要一份运行时

站点本身是纯静态页面，双击 HTML 就能打开，剧情、篇章、角色、搜索全部可用。 只有接入需要一个 JavaScript 运行时来跑那个服务脚本——不需要装任何第三方包。

服务全程只读：不写任何文件、不联网。它读的就是本站这份数据，没有第二份副本。
